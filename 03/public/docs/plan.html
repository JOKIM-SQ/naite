01누가 쓰나

같은 사무실/팀 동료 2인 이상. 매일 커피 살 곳을 정하는 데 카톡으로 의견이 흩어지는 사람들.

02지금은

단톡방에 각자 의견을 텍스트로 던지고 누가 세는지도 없이 흐지부지 정해진다. 매번 반복.

03없앨 동작 하나

단톡방 스크롤 올려서 누가 뭘 제안했고 몇 명이 좋다고 했는지 눈으로 세는 것.

04핵심 기능 1개

Auth.js(Credentials)로 로그인한 사용자가 커피 아이디어(제목 1개)를 올리고, 본인 글을 수정·삭제할 수 있으며, 본인 글을 제외한 아이디어에 계정당 최대 3표까지 찬성 투표하면 투표 결과가 모든 계정에서 동일하게 보인다.

05안 만드는 것 3개

  • 댓글
  • 회원가입 커스텀 UI·비밀번호 재설정·소셜 로그인 — Auth.js Credentials(이메일/비밀번호)만
  • 검색·카테고리·투표순 외 추가 정렬

06성공 판정

  • 테스트 계정 2개가 각자 로그인해 아이디어를 올리고 서로에게 투표한 결과가 양쪽 모두에서 동일하게 보인다.
  • 본인 글은 수정·삭제되고, 남의 글은 서버 API가 403으로 막는다.
  • 본인 글 투표 차단, 계정당 3표 한도, 중복 투표 차단이 모두 동작한다.

07내 옵션 + 이유

Auth.js(@auth/core)는 세션을 JWT httpOnly 쿠키로만 다루고 특정 DB에 종속되지 않아, 로그인 로직을 서버 함수 안에 가볍게 둘 수 있다. 이번 주 원래 선택지 4개(Supabase Auth·Firebase Auth·Clerk·Auth.js) 중 Auth.js로 바꿔, RLS 대신 서버 코드가 직접 소유권·투표 한도를 검증하는 방식을 겪어본다. 비밀번호는 평문 저장 없이 해시로 저장한다 — 처음엔 bcrypt를 쓰려 했으나 Vercel Edge 런타임 번들링에서 깨져서, Edge에 내장된 Web Crypto API로 PBKDF2(SHA-256, 100,000회, 계정별 랜덤 salt) 해시를 직접 구현했다.

08리스크 + 검증법

걱정되는 것: RLS 없이 서버 API에서 본인 글 투표 금지·투표 한도 3표를 코드로 직접 강제하는 게 실제로 막히는지, Auth.js JWT 세션 쿠키가 Vercel Edge 함수에서 제대로 읽히는지, bcrypt 대신 만든 PBKDF2 해시가 실제로 검증(로그인)까지 되는지.
화요일 스파이크로 확인: 테스트 계정 2개로 로그인 → 세션 쿠키로 `/api/auth/session` 확인 → 본인 글 투표 시도 → 4번째 투표 시도 → 남의 글 수정 시도, 넷 다 실제로 막히는지 직접 눌러본다.
