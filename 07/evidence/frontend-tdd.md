# S07 프런트엔드 검증 기록

날짜: 2026-09-16

## 범위

- `public/index.html`, `public/app.js`, `public/styles.css`, `public/favicon.svg`
- `public/receipt-view.mjs`, `public/receipt-view.test.mjs`
- 정적 HTML/JS, native `node:test`. 테스트 프레임워크·샘플 영수증·가짜 API 대체 없음.
- API 계약은 `07/PLAN.md`, 입력 한도는 `lib/receipt-values.mjs`와 확인했다.

## 테스트 우선 구현

1. 값 파싱·파일 검증·자동저장 핵심 9개 테스트를 먼저 작성했다. 빈 인터페이스 스텁 상태에서 모두 assertion 실패를 확인했다(RED 0/9).
2. 실제 구현 후 9/9 통과했다(GREEN).
3. 서버의 금액 상한 1e12·ISO 통화·텍스트 길이·파일명 제한을 추가 테스트했다. 제한 미구현 상태에서 2개 assertion 실패 후 구현해 11/11 통과했다.
4. 409 원격 품목 추가/삭제와 반복 충돌 제한 회귀를 추가해 13/13 통과했다.
5. 지연 응답 중 새 빈 품목 유지, 원격 배열 구조 변경 중 미확정 품목 입력 보존 테스트를 추가했다. reconciliation 스텁에서 2개 assertion 실패(13/15)를 확인하고 구현 후 15/15 통과했다.

명령:

```sh
node --test 07/public/receipt-view.test.mjs
node --check 07/public/app.js
```

최종 결과: 테스트 15개 pass, fail 0. app.js 구문 검사 exit 0.

## 보장하는 동작

- 빈 숫자를 0으로 발명하지 않음, 윤년 날짜 검증, 금액 구분자·소수 유지.
- JPEG/PNG/WebP 3 MiB 상한, 한 번에 3장, HEIC 및 파일명/빈 파일 오류 안내.
- 개별 사진 업로드 → 분석 → 저장 자동 실행. 실패 사진만 재시도.
- 450ms debounce, 영수증별 저장 직렬화, 최신 revision 사용. 지연 응답으로 최신 수정값을 덮어쓰지 않음.
- 409 시 최신 GET 결과에 실제 로컬 변경 필드만 재적용. 연속 충돌은 한 번만 자동 복구 후 입력 보존 및 재시도 안내.
- 원격 품목 구조가 바뀌면 필요한 행만 재구성. 아직 입력 중이거나 오류가 있는 품목은 DOM 행과 원시 입력 보존.
- 빈 새 품목은 이름 입력을 기다린 뒤 저장하며, 앞선 저장 응답이 빈 새 행을 없애지 않음.
- 수정 횟수는 서버 응답만 사용. 상호/날짜/금액/통화/품목의 변경 필드 기준이며 품목 전체는 1개 필드임을 표시.
- 최초 추출값 details 제공. 정답 확인 전 정확도 N/3, 신뢰도 등 숫자를 표시하지 않음.
- 최초 GET으로 세션을 만든 뒤 업로드 허용. 저장된 processing은 GET으로 완료 상태 복원.
- 날짜/금액 요약표의 파일명에서 해당 원본·편집 카드로 이동.

## 검증 한계 및 인계

- 이 worker는 전역 브라우저를 사용하지 않았다. `/browse` 기반 실제 390px·키보드·업로드/편집 QA는 메인 에이전트가 담당한다.
- 별도 검증 에이전트가 실제 app.js를 Node VM + 최소 DOM으로 실행해 6개 시나리오 통과를 확인했다: 원격 품목 추가/삭제 중 editing/invalid 원시값과 기존 노드 보존, 이후 change 값이 queueSave를 거쳐 저장 대상으로 전달, 편집 없는 원격 품목 추가/삭제의 행 수 갱신. 이는 실제 브라우저 검증을 대체하지 않는다.
- 실제 Supabase/Claude 호출, 사진 3장 정확도, 실제 저장 지속성은 외부 자격증명과 실제 영수증으로 별도 확인해야 한다. 이 문서는 그 통과를 주장하지 않는다.
- 커밋하지 않았다. 할당된 파일 외 변경하지 않았다.
