# S08 연결·검증 기록

## 확인한 사실

- 가이드 S08은 여러 사용자의 값 변경을 두 탭에서 동시에 확인하고, 반영 지연·연결 관리·충돌·비용과 폴링 대안을 설명하는 과제다.
- 기존 Supabase `weekly-awe-project`를 사용한다. S08 전용 객체만 추가한다.
- 공식 CLI로 프로젝트 연결 및 public 스키마 읽기 쿼리에 성공했다.
- 변경 전 `s08_*` 테이블이 없고 `supabase_realtime` publication이 존재함을 확인했다.

## 실제 Supabase 검증 · 2026-09-23

자동 검증에는 전용 임시 계정과 보드를 사용했다. 실제 사용자 데이터는 사용하지 않았다. Admin으로 생성한 임시 계정의 실제 Supabase 인증 세션으로 동작을 검증했으며, 이후 사용자가 로컬 앱의 Google 로그인 완료를 직접 확인했다.

- 소유자 보드 생성 → 다른 계정 초대 참여 성공. 소유자만 초대값 조회 가능.
- 외부 계정의 품목 조회 결과 0행, 변경 RPC 거절. 멤버의 테이블 직접 UPDATE도 거절.
- 보드 멤버의 실제 Realtime UPDATE 수신, 외부 계정에는 해당 변경이 전달되지 않음.
- 두 계정이 동시에 출고한 10건 모두 반영: 25 → 15.
- 같은 요청 ID를 동시에 6회 보내도 한 번만 차감: 15 → 13. 다른 delta 재사용과 음수 재고는 거절.
- Node SDK 요청 시작 → 다른 계정 SDK 이벤트 수신 5회: 465, 495, 534, 543, 523ms. 브라우저 DOM 반영 시간과 다른 지표다.

## 실제 두 탭 화면 반영 측정

로컬 앱 `http://127.0.0.1:3080/` + 원격 Supabase(us-east-2), 같은 Chromium의 두 탭/같은 QA 계정. 탭 A의 입고 버튼 클릭 직전 시각에서 탭 B의 MutationObserver가 해당 수량을 확인한 시각까지 측정했다. 양쪽은 DB를 실제 조회하며 측정기만 추가했다. 네트워크 지연 조작 없는 20회 연속 표본이다.

| 표본 수 | 최솟값 | 중앙값 | p95 (nearest rank) | 최댓값 |
| --- | --- | --- | --- | --- |
| 20 | 0.357초 | 0.536초 | 0.675초 | 0.829초 |

원시 값(ms): 829, 357, 657, 431, 623, 434, 675, 519, 586, 425, 604, 490, 518, 589, 540, 426, 613, 445, 618, 531.

이는 한 환경의 관찰치다. 다른 기기·네트워크나 여러 명의 부하 성능을 보장하지 않는다. Google 로그인 완료는 사용자 확인으로 기록한다. 배포 주소에서의 측정과 실제 월 비용은 기록 없음.

## 연결과 UI 관찰

- UI에서 품목 등록 후 두 번째 탭에 동일 품목 표시.
- 재고 34에서 -999 요청을 거절하고, 입력창에 범위 오류를 표시하며 수량 34 유지.
- 한 탭 오프라인 중 다른 탭에서 33 → 34 변경. 네트워크 복구 후 새로고침 없이 34 확인. 개선본에서는 즉시 끊김 표시·등록/입출고 잠금·스냅샷 34 유지, 복구 후 35로 자동 갱신 및 버튼 활성화까지 확인.
- 390px 모바일에서 가로 넘침 0. 로그인·재고 목록·품목 입력을 브라우저로 확인.
- 새 보드 생성과 빈 상태 확인. 클립보드 권한 거절 시 초대 링크 대화상자가 열리고 읽기 전용 링크 전체 선택·닫기가 가능함을 확인. 초대 토큰은 기록하지 않음.
- 설정 API 실제 GET 200(공개 설정만), POST 405. 타입 검사·구문 검사·빌드 및 테스트 39/39 통과.
- 로그아웃 후 재고 행 0개·workspace 숨김·초대값 제거 확인. Google 시작 버튼은 실제 accounts.google.com 로그인 화면으로 이동한다. 이후 사용자가 로컬 앱의 Google 로그인 완료를 직접 확인했다. 인앱 브라우저 세션을 자동 검증용 Chromium에서 읽은 것은 아니다.
- 검증 종료 후 해당 실행이 생성한 QA 계정 3개와 소유 보드만 정리 완료.
- 사용자 로그인 완료 후 읽기 전용 집계에서 보드·멤버·품목 모두 0개임을 확인했다. 이는 보드 생성 전 초기 상태이며, 사용자의 보드 진입이나 품목 등록을 관찰했다는 의미는 아니다.

## 발견한 문제와 수정

초기 `SUBSCRIBED`가 PostgreSQL 변경 구독 활성화보다 먼저 도착해 첫 이벤트가 누락될 수 있었다. 공식 SDK 2.116.0의 `postgres_changes_options: { wait: true }`를 사용해 서버의 실제 구독 준비 확인 후 스냅샷을 읽도록 수정했다. SQL/RLS를 완화하지 않았다.

브라우저 오프라인 시 heartbeat 이전에는 연결 표시가 남는 문제를 발견했다. offline 이벤트에서 채널 세대를 종료하고 마지막 스냅샷을 유지하며 변경을 잠그도록 보완했다. online 이벤트에서 새 채널 연결 후 스냅샷을 재조회한다. 개선본 브라우저 검증 통과.

서로 다른 품목을 조작할 때 먼저 보낸 변경 응답이 다른 품목의 조정창을 닫거나 잠그는 경합을 리뷰에서 발견했다. 요청 품목과 현재 조정창 품목이 일치할 때만 해당 창을 갱신하도록 고쳤으며 성공/실패 두 경로 회귀 테스트를 통과했다.

첫 저장 소요 시간은 별도 시작 타이머가 없어 기록 없음. 계정 월별 사용량·실제 비용도 미측정이다.

## 공개 배포 검증 · 2026-09-23

- 공개 주소: https://s08-stockroom.vercel.app/ . Vercel 프로젝트 `s08-stockroom`, 프로덕션 배포 `dpl_AQdJ6SgXxnG5YRYwU45qF5JvJjrb`가 READY이고 해당 별칭이 연결됨을 확인했다.
- CLI 59.26.0으로 `08/`에서 직접 배포했다. 프로젝트 루트는 `.`, Node.js 24.x이며 Git 자동 배포는 연결하지 않았다. 원격 소스는 `codex/s08-realtime-inventory` 브랜치에 반영했다.
- Production에는 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`만 등록했다. 서비스 역할 키나 다른 주차 API 키를 등록하지 않았다.
- 실제 브라우저에서 비로그인 공개 접근 200, Google 시작 버튼 활성화, 데스크톱·390px 모바일 화면을 확인했다. 모바일 scrollWidth와 viewport 모두 390px이며 가로 넘침이 없다. 정상 홈 진입에서 콘솔 오류 없음.
- `/api/config` 200, 반환 키는 `url`, `publishableKey`, `provider`뿐이며 올바른 Supabase 프로젝트와 Google 공급자를 가리킨다. `/docs/plan.html`, `/docs/report.html`, `/icon.svg`, `/vendor/supabase.js` 모두 200이다.
- 배포된 리포트의 서비스 URL과 기획서의 원격 소스 링크가 실제 주소와 일치한다.
- `/.env.local`, `/.qa/live-report.json`, `/SUPABASE.sql` 모두 404다. 배포 파일 목록에서도 환경 파일·QA 산출물·Supabase 로컬 파일이 제외됨을 확인했다.
- 공개 앱의 로그인 버튼을 클릭해 실제 `accounts.google.com` 인증 화면으로 이동함을 확인했다. 요청한 반환 주소는 공개 앱이다. Google 인증 완료 후 공개 앱 복귀까지 검증한 것은 아니다.
- Supabase 관리 화면은 자동화 브라우저에 로그인되어 있지 않아 Redirect URLs에 공개 주소를 추가하도록 사용자에게 요청했다. 기존 Site URL과 다른 주차 반환 URL은 변경하지 않았다. CLI `config push`는 일부 인증 설정과 반환 URL 목록을 덮어쓸 수 있어 단일 URL 추가에 사용하지 않았다.
- 이후 사용자가 `https://s08-stockroom.vercel.app/` 반환 URL 추가 완료를 확인했다. 공개 홈 200 및 로그인 버튼의 실제 Google 인증 화면 이동을 재확인했다. 자동화 브라우저에는 Google 세션이 없어 인증 완료 후 공개 앱의 보드 화면으로 복귀하는지는 사용자에게 확인을 요청했다.
- 배포 직전 타입·구문·테스트 39/39·빌드 검사를 재실행해 모두 통과했다. 지연 시간 표본은 앞서 기록한 로컬 UI와 실제 원격 DB 조합의 측정값이며, 프로덕션에서 다시 측정한 수치로 해석하지 않는다.

## 기술 판단

작은 팀 MVP에서 설정이 간단한 Postgres Changes를 사용한다. 구독자가 많아지면 각 변경의 권한 검사 비용을 고려해 Broadcast를 검토한다. DB 변경은 원자적인 delta RPC로 처리하고 요청 UUID로 재시도를 구별한다.

5초 폴링도 느긋한 재고 확인에는 가능하다. 변경 시점이 균일하게 분포한다는 가정에서 평균 대기 2.5초에 네트워크·렌더링 시간이 더해진다. 두 탭이면 변경이 없어도 분당 24회 조회한다. 즉시 반영을 시연하는 이번 과제에는 Realtime이 적합하다. 이는 계산 예시이며 관측 지연이 아니다.
