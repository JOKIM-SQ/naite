# RELAY 화면 설계

구현된 화면의 설계와 검증 경계를 기록한다. 실제 목록·실패 상세·타임라인은 화면과 API 기록으로 확인했다. 2026-10-23에는 실제 Claude 분류·초안·복합 문의 검토 필요와 자동·수동 복구 결과까지 확인했으며, `SUBMISSION.md`의 증거가 있는 항목만 완료로 본다.

## 첫 화면

따뜻한 오프화이트 바탕, 짙은 잉크색 본문, 산호색 주요 행동을 사용한다. 작은 사이드바로 앱 이름과 작업함 위치를 알리고, 상단의 한 문장으로 “문의 접수 후 분류와 답변 초안을 만든다”는 역할을 설명한다.

상단 KPI는 현재 작업공간의 실제 문의에서 계산한다. 문의 목록과 상세를 함께 놓고, 선택한 문의의 원문·분류 근거·초안·실행 타임라인을 같은 화면에서 확인한다. 문의가 없으면 빈 상태와 새 문의 행동을 제공한다. 가짜 문의나 미리 계산한 성공 수치를 넣지 않는다.

## 주요 행동

| 위치 | 행동과 피드백 |
| --- | --- |
| 새 문의 모달 | 제목·고객명·채널·본문 입력, 원문 프리셋 선택, 실제 API 접수 |
| 접수 결과 | AI 완료를 기다리지 않고 접수 사실을 표시 |
| 목록 | 현재 상태·문의 제목·검토 필요 여부를 확인하고 상세 선택 |
| 상세 | 원문과 AI 분류·우선순위·이유·답변 초안을 비교 |
| 실행 타임라인 | 실제 기록의 시각·단계·시도 횟수·실패 내용을 표시 |
| 최종 실패 | 오류를 유지하고 다시 시도 제공; 의도적 실패 조건 해제 후 재접수 |

## 상태 표현

- `queued`, `classifying`, `drafting`, `retrying`, `completed`, `failed`는 서버 상태를 따른다.
- `needs_review`는 시스템 오류와 별개다. 완료된 작업도 사람이 분류와 초안을 검토해야 할 수 있다.
- 채널 선택은 문의 메타데이터이며 이메일·채팅 서비스와 실제 연결되었다는 뜻이 아니다.
- 일시 실패·지속 실패는 데모임을 표시한다. 결과와 재시도 횟수는 실제 실행에서 읽는다.
- 답변은 항상 초안으로 표시한다. 발송 버튼과 발송 완료 상태는 만들지 않는다.

## 접근성과 반응형

좁은 화면에서는 목록과 상세를 순서대로 읽을 수 있게 배치한다. 폼 라벨, 명확한 포커스, 키보드 모달 조작, 상태 전달을 제공한다. 모션 감소 설정을 존중하고 진행 상태를 애니메이션만으로 전달하지 않는다. 실제 지원 여부는 브라우저 검증으로 확인한다.

앱 디자인은 팀 제출 HTML에 적용하지 않는다. 제출 문서의 스타일과 구조는 팀 템플릿 그대로 둔다.

실제 실패 화면은 `.qa/relay-desktop-final.png`, `.qa/relay-failed-final.png`에 기록했다. 2026-10-23 실제 완료·검토 필요 결과는 `.qa/claude-final-20261023.json`과 `SPIKE.md`의 후속 검증 절에 기록했다. 원본 QA 파일은 Git·배포에서 제외되며, 단위 테스트와 실제 실행 근거를 구분한다.
