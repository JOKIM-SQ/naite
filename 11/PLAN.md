# S11 RELAY · 릴레이

CS 문의를 먼저 접수하고, Inngest가 나중에 분류와 답변 초안을 만드는 작업함이다. 구현과 실패 경로 검증은 진행했으며, Claude API 키 설정 후 정상 처리 검증이 남아 있다. 실제 판정은 `SUBMISSION.md`에서 별도로 관리한다.

## 누가 쓰고, 어떤 동작을 줄이나

문의가 들어오면 내용을 읽고 유형·우선순위를 정한 뒤 첫 답변을 작성하는 CS 담당자가 사용한다. 사람이 매번 시작해야 했던 분류와 초안 작성을 접수 직후 작업으로 넘긴다. 기존 처리 시간과 절감 시간은 측정 전이므로 기록 없음이다.

## 하나의 흐름

1. 새 문의에 제목·고객명·본문·채널을 입력한다. 입력 예시는 원문 프리셋이며 저장된 결과가 아니다.
2. 서버는 브라우저 작업공간에 문의를 저장하고 Inngest 이벤트 수락 후 HTTP 202를 반환한다.
3. Inngest가 분류, 답변 초안, 완료 저장을 독립 단계로 실행한다. 화면은 실제 저장 상태를 갱신한다.
4. 완료된 문의의 유형·우선순위·판단 근거·답변 초안을 확인한다. 낮은 신뢰도와 애매한 내용은 `검토 필요`로 구분한다.
5. 작업 오류는 실제 재시도·최종 실패로 표시하며, 최종 실패한 문의만 다시 접수한다.

## 안 만드는 것 3개

- 회원가입·로그인 및 팀 권한 관리
- 외부 메일함 연결과 문의 자동 수집
- 답변 자동 발송 및 고객에게 보내기

## 성공 판정과 검증 시나리오

| 시나리오 | 확인할 결과 | 현재 상태 |
| --- | --- | --- |
| 일반 문의 | 접수 응답이 AI 완료 전에 돌아오고, 실제 분류·초안이 저장됨 | 실제 접수 확인; 분류·초안은 API 키 설정 대기 |

## Inngest를 고른 이유

문의 접수 요청과 오래 걸리는 AI 작업의 수명을 분리하고, 분류·초안 생성 단계와 재시도를 코드로 추적하려는 선택이다. 실패한 실행과 다시 실행한 작업을 구분하는 서버 내부 run token을 사용한다. 실제 Inngest 재시도와 최종 실패는 확인했지만 정상 AI 처리와 최종 적합성 평가는 키 설정 후 진행한다.

## 리스크와 확인 방법

- 이벤트 수락 실패: 성공으로 숨기지 않고 API 오류와 저장된 실패 상태를 확인한다.
- 재시도 경합: 이전 run token의 작업과 실패 핸들러가 새 실행을 덮어쓰지 못하는지 확인한다.
- 부정확한 분류: 복수 범주·정보 부족을 포함한 실제 입력으로 검토 필요 표시를 확인한다. 분류 정확도는 정답 대조 전 추정하지 않는다.
- 비밀키·문의 혼선: 서버 전용 키, HttpOnly 작업공간 쿠키, Supabase service_role 접근 제한을 확인한다.
- 데모 비교 질문: **“이걸 n8n으로 했으면 몇 분이었을까”**. n8n으로 직접 측정하지 않았으므로 소요 시간은 기록 없음으로 둔다.

팀 HTML은 `_template/public/docs/`의 구조·CSS·data-f·복사 스크립트를 보존한다. 실제 배포와 갤러리 등록은 별도 단계다.
